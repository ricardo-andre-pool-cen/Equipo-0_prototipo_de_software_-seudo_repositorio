# OUR PROCESS, CHANGES TO ACHIEVE EFECTIVENESS

The main theme for the second delivery was to get some professionalism and apply the hit methodology **SCRUM** to work our project better. In order to achieve it we needed to apply a lot of changes in our current process back then:

- ## INDIVIDUAL CONTRIBUTION METRIC

Unless we planificate as timewatchers gods, we can't just keep dividing the entire project in 100 points and dividing their asignation equitably among the team members, we just don't know when the things are going to change due to problems, instead, we needed to change the amount of asigned tasks constantly while the documentation keeps increasing.

We decided that we were going to evaluate ourselves with the github project "issues" feature, where everyone constantly gets asigned new tasks that are needs for the project. So now a member is evaluated with the difference between asigned tasks and completed tasks.

- ## DOCUMENTATION

Just before the advice, the team was already debating if we needed to keep double documentation for both languages (english and spanish), and after the advice, it was clear that it was useless. We also noticed that our Canva virtual boards where not even seen, so we did a lot of useless work during the first deliver.

The main change about that now is that we will only be written content in english, and we will limit the use of Canva to only if necessary for an artifact, graph or something.

In order to apply the use of "sprints" from the scrum process, we decided to divide our time in four sprints of nearly one week each of them, we created four folders to document them, this folders contain the "dailys" of the team, that is, register of all the activity done by each member to contribute to the project per day. We are supposed to be able to see how the project went evolutioning during the sprints.

We also learned to use markdown format in the repository files not only to make a beautifuler text, but to link all the information in the README files, so it's easier for any user to navigate and find information inside our repository.

- ## THE IDEA

The objective of the worked idea during the first deliver, was to teach the young people to use a repository, in order for them to comprenhend the environment of git and github. But we wanted to reach that by creating a whole new version control software, supposed to be simpler but enough for the young users to learn how to deal with this environment. After some advice, we saw it clear: that proposal is not going to achieve our objective, it would even create more problems, or it could be forgotten very soon.

We needed help to continue with the project. We check again our objective: "teach the young people to use a repository", with enough advice we got clear that our objective was to teach git, but there are actually thousands of contents out there in the internet to do that, however most of the content is just documents and text, which is difficult to understand for many people beginning to learn git.

People could learn how to do git actions, with a lot of work, with that in mind, we finally decided that the new objective of the project will be, we saw value in: "help beginner users learning git to comprehend it through another environment than just text". With a real valuable idea we started to work again with the artifacts, but now with a better understanding of all this FIS subject, with **SCRUM** process, with better planning, but less time.

- ## REQUIREMENTS

Back then in the first delivery, we had our requirements written by the classic method in two documents: "Act#3 Requisitos funcionales" and "Act#4 Requisitos no funcionales"; just before the idea got discarted we wanted to keep those two documents and the classic method redaction along with the brand new user stories, and we thought about just passing the functional requirements to user stories and keeping non-functional requirements without changes.

After the reset of the idea, we needed to delete all our requirements, but we saw our mistakes in our old method to deliver requirements and we saw an opportunity to apply **SCRUM** artifact user stories better. We decided to only make the new requirements in user stories format, we delimited the requirements we would work in the short time and in base of that we made the design. So now we only have one document to implement the requirements: "Artifact#3 User stories"; and we have a short amount of them, assurancing that we will work on all of those.

## GITHUB PROJECT

In order to practice a better control of our tasks, it was decided to use the github project "issues" feature, where we created "issues" that represented the needs of the repository, these are tasks that can be asigned to the members so we get to divide the responsabilities among all the team. Inside the description of every task we used the **SCRUM** artifact "definition of done", that is a bunch of criterias that must be fulfilled to set the tasks as completed, so now we can tell where the document should be placed inside the repository or what especific information must have.

Inside the github project, we created some "cards" that would help us to set a category of progression for every task: "Backlog", "ToDo", "In progress", "In review" and "Done"; we were carefully in keep the followment of this artifact and changing the tasks from category to category acording to the progress of the second delivery.

## NEW PRODUCT DESCRIPTION

### THE PROBLEM

Most of the people that starts to learn Git can't learn quickly and easy how to use it correctly from the content available in internet, this is because the text blocks are difficult to understand, and they can't see clear examples of usage and they do not finish comprehending the action.

### SOLUTION PROPOSAL

An environment where all the posible information and guides about Git is deposited, builded for unexperienced people, where the content is presented with a lot more tools like graphs and playable audios than just text. Not only that, the people could verify if they have learn it through evaluations presented with different styles and tools.

### OBJECTIVE

This is meant to help people to comprehend git and to improve their tech-skills in this tool.

### USERS

This environment is supposed to be used by:

- Unexperienced people that wants to learn git
- Experienced people that wants to remember something from git
